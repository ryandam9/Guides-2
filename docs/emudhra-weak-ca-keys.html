Incident report · October 2026 · Bug 2083449

Eight keys, 256 guesses

A trusted certificate company made eight secret keys that were too weak. Anyone with a laptop can find these keys in less than one second.

With these keys, a person can make a fake "ID card" for any website. This page tells you what occurred, how it occurred, and what you must do.

Part 2

How root and intermediate CAs work

Your browser does not know each website. It knows only about 150 roots. It follows a chain from the website up to a root.

One root, many intermediates

A CA has a small number of roots. Each root signs some intermediates. Each intermediate signs many customer certificates.

Why a CA uses two levels

If an intermediate key is lost, the CA revokes only that intermediate. The root continues to operate. If a root key is lost, all certificates below it fail, and each device must get an update.

Why new certificates need no update

Your browser does not keep a list of all certificates. It only checks the signatures up to a root. A certificate that a CA signs today works immediately.

How a website gets a certificate

  1. The website owner makes a key pair and a CSR on the server.
  2. The CA checks that the owner controls the domain. For OV and EV, the CA also checks the company.
  3. The intermediate HSM signs the certificate.
  4. The CA records the certificate in public Certificate Transparency logs.
  5. The owner installs the certificate and the intermediate on the server.
  6. Your browser gets both, checks the chain to a root, and shows the padlock.

Part 4

What is necessary to make CA keys

A CA does not make its keys on a usual computer. The rules tell it to use special equipment, a secure room and a team of trusted persons.

HSMA certified, tamper-resistant box (FIPS 140-2/140-3 Level 3 or Common Criteria EAL4+). It makes the key and keeps it inside.
True random sourceA part of the HSM that makes unpredictable numbers. The private key comes from these numbers.
Offline computerA laptop with no network. It sends commands to the HSM.
Secure roomA locked room with an access log. Only approved persons can go in.
Trusted personsStaff with checked backgrounds. Each has one smart card. The HSM needs some of the cards (for example 3 of 5).
Written scriptA list of each command and step. The team must not change it on the day without approval.
Witness and videoAn independent auditor watches, or a camera records all steps.
Encrypted backupA copy of the key, locked with a key that only the HSM can use. It goes in a safe.
Part 5

The key generation process

The HSM makes a random private key. From the private key, it calculates the public key. The private key must never go out of the HSM.

Steps of a key ceremony

  1. Write the ceremony script. Get approval from management and from the auditor.
  2. Go into the secure room. Make sure that the tamper seals on the HSM and the laptop are not broken. Record the seal numbers.
  3. Start the video recording. The leader reads each step aloud. The auditor watches each step.
  4. Start the offline laptop. Make sure that it has no network connection.
  5. Activate the HSM. The key custodians put in their smart cards.
  6. Generate the key pair inside the HSM. Give the key a clear, unique label.
  7. Make the CSR from the new key.
  8. Make sure that the public key in the CSR agrees with the key in the HSM. Test the public key for weakness. eMudhra did not do this
  9. Sign the certificate. A root signs itself. For an intermediate, the offline root HSM signs the CSR.
  10. Make an encrypted backup of the key. Put the backup and the smart cards in the safe.
  11. Stop the HSM. Put new tamper seals on the equipment. Stop the recording.
  12. All persons sign the ceremony record. The auditor writes the key generation report.
Where eMudhra's process failed

eMudhra added an extra step to the script (the wrap and unwrap test). This step made a second, weak key with an almost identical label. In step 7, staff used the weak key. Nobody did step 8. A process audit checks that the team follows the script. It does not check the key itself.

Example: a new website gets a certificate

  1. Priya owns shop.example.com. She runs Certbot on her server.
  2. Certbot makes a new key pair on the server. The private key stays on the server.
  3. Certbot sends a CSR to Let's Encrypt.
  4. Let's Encrypt asks Certbot to put a test file on the website. This proves that Priya controls the domain.
  5. The Let's Encrypt intermediate (for example R11) signs the certificate. Let's Encrypt records it in the CT logs.
  6. Certbot installs the certificate and the intermediate. Each 60 to 90 days, Certbot does all the steps again.
  7. You open the shop. Your browser gets the certificate and R11. It finds ISRG Root X1 in its root list and shows the padlock.
# Step 2 and 3, made by hand with OpenSSL
openssl ecparam -genkey -name prime256v1 -out shop.key   # private key: keep it secret
openssl req -new -key shop.key -subj "/CN=shop.example.com" -out shop.csr   # CSR: send to the CA

# Or let Certbot do all the steps
sudo certbot --nginx -d shop.example.com

Example: see a real chain

You can see the chain that any website sends. Run this command:

openssl s_client -connect www.google.com:443 -showcerts </dev/null | grep -E "^ *[0-9] s:|i:"

 0 s:CN = www.google.com
   i:C = US, O = Google Trust Services, CN = WR2          # the intermediate signed it
 1 s:C = US, O = Google Trust Services, CN = WR2
   i:C = US, O = Google Trust Services LLC, CN = GTS Root R1   # the root signed WR2

"s" is the subject (who the certificate is for). "i" is the issuer (who signed it). The root is not in the output, because your device already has it. The names can change when Google changes its certificates.

Example: the same parts in the eMudhra incident

Who made the error

The CA (eMudhra) made the intermediate keys in its key ceremony. The weak keys came from that step. The website owners, root programs and browsers did nothing wrong.

Who made the fix

  • Browser makers: block lists (OneCRL, CRLSet)
  • Root programs: removed the G3 root
  • Package maintainers: new certifi, ca-certificates, Go
  • CAs: eMudhra and Sectigo revoked the certificates
Part 7

How the error occurred

On 30 April 2025, eMudhra did a "key ceremony". In a key ceremony, staff use an HSM to make new CA keys. They made 24 intermediate certificates that day.

The 24 keys were in three series (A, B and C). Each series had RSA keys and ECC (P-384) keys. The eight weak keys are all the ECC keys in series B and C.

  1. eMudhra changed its usual procedure. It added a test that wraps and unwraps keys, because these keys had to go to data centres in Europe and the USA.
  2. The HSM made the correct, strong ECC keys.
  3. An error in the script made a second set of ECC keys. These keys were very weak.
  4. The labels of the strong keys and the weak keys were almost the same. Staff used the weak keys by mistake.
  5. The eMudhra root signed the eight weak keys. In May 2025, Sectigo also cross-signed them.
Another possible cause

Some experts think that the HSM software wrote a "reference" key file to disk. This file only points to the real key inside the HSM. They think that a tool used this small reference number as a real private key. eMudhra has not yet given a full root-cause report.

The warning sign that eMudhra missed

In May 2025, the lists of revoked certificates (CRLs) from these six TLS intermediates had bad signatures (Mozilla bug 1970728). The real HSM key signed the lists, but the certificates had the weak public key. So the signatures did not agree. eMudhra then signed the lists again with the weak keys. It did not find the real problem.

Part 8

Why the keys were so weak

A P-384 private key must be a random number between 1 and a very large number. That large number has 116 digits. Nobody can guess it.

Each of the eight weak keys was a number less than 256. In computer memory, the key was all zeros, with only the last byte different.

To find the key, a person makes the first 255 P-384 keys. Then the person compares each one with the public key in the certificate. One will agree. This takes less than one second.

Part 9

What an attacker can do with the key

What the attacker needs

The leaked key (easy to get), and control of your network connection. Examples are a fake Wi-Fi hotspot, a bad router, or DNS tricks.

What makes the risk lower

eMudhra says that the eight intermediates did not issue certificates to customers. Chrome found no fake certificates in the public Certificate Transparency logs. No attack is known at this time.

Part 12

How Go fixed it

Go does not check revocation, and it has no root list of its own. So the Go team added a small block list to the standard library. The change has 42 new lines in three files. It removed no lines.

Note: the code and the release notes do not name eMudhra. They only say "a handful of intermediates".

The idea: block the key, not the certificate

Where Go checks a chain

Go has three ways to check a certificate chain. The fix had to go into all three.

// verify.go — Verify() picks the verifier (code before the fix, abridged)
if runtime.GOOS == "windows" || runtime.GOOS == "darwin" || runtime.GOOS == "ios" {
    systemPool := systemRootsPool()
    if opts.Roots == nil && (systemPool == nil || systemPool.systemPool) {
        return c.systemVerify(&opts)   // returns early: Go's own checks never run
    }
    ...
}
// Linux, and any custom Roots pool, continue to Go's own chain builder

This is why one check in verify.go was not sufficient. On macOS and Windows, systemVerify returns before Go's own checks.

  • There are 8 entries, one for each weak key.
  • Each entry is the SHA-256 hash of a certificate's public key part (SPKI), written as 64 hex characters.
  • map[string]struct{} is Go's usual way to make a set. Only the key is important. The value {} uses no memory.
  • A lookup in a map is very fast. The check adds almost no time to each connection.

Step 2. The check function verify.go · new

+// containsDistrustedSPKIHash checks if any of the certificates in the chain
+// have an SPKI whose hash is present in the distrustedSPKIHashes map.
+func containsDistrustedSPKIHash(chain []*Certificate) bool {
+	for _, c := range chain {                                   // each certificate: leaf, intermediates, root
+		h := sha256.Sum256(c.RawSubjectPublicKeyInfo)            // hash the raw SPKI bytes
+		if _, ok := distrustedSPKIHashes[hex.EncodeToString(h[:])]; ok {   // in the list?
+			return true                                          // yes: this chain is bad
+		}
+	}
+	return false
+}

The function looks at every certificate in the chain, not only the leaf. So a chain fails if it goes through one of the weak intermediates. The change also adds two imports, crypto/sha256 and encoding/hex.

Step 3. Go's own verifier verify.go · Verify()

+       return true

if len(candidateChains) == 0 {
    ...
    err = CertificateInvalidError{c, NoValidChains, strings.Join(details, ", ")}

  • Go first builds all possible chains from the leaf to a trusted root.
  • slices.DeleteFunc removes each chain for which the function returns true. Go already used it to remove chains with bad policies, key usage or name rules.
  • The fix adds one more rule at the end: remove the chain if it has a blocked key.
  • If no chain is left, Verify returns an error. Your program sees: tls: failed to verify certificate: x509: no valid chains built.
  • This path covers Linux, and every platform when you give your own VerifyOptions.Roots pool.

What the fix does not do

  • It does not remove the emSign G3 root. Other G3 certificates still work in Go until your OS or distro removes the root.
  • It does not add revocation checks. It blocks only these 8 keys.
  • It does not change binaries that you built before. You must rebuild them.
  • It adds no tests in this commit.

Part 13

What you must do

For all users

  1. Update your browser.
  2. Update your phone and computer operating system.
  3. Do not ignore a certificate warning.
  4. Do not use public Wi-Fi for banking until your devices are updated.

For developers

  1. Run pip install -U certifi.
  2. Update ca-certificates on each server.
  3. Rebuild container images from new base images.
  4. Update Go, Node.js and the JDK. Bump webpki-roots.
  5. Find sites that use emSign G3 certificates. Replace those certificates.
Test your browser

Open emudhra.we-have-a-problem.com. If your browser is safe, all the test connections fail.

Part 14

The lesson

The HSM had a FIPS 140-2 Level 3 certificate. But a human error in a script made the keys weak. A certified box does not stop a bad procedure.

The weak keys were in public certificates for 18 months. A free tool found them in a few minutes. Nobody had done that simple check before. Experts now ask CAs to test each new public key for this type of weakness.
