Why your Spark app gets no YARN resources

Do not start with the settings. Start with the symptom. Run one command and read the state of the app. The state tells you which of five cases you have. Each case has one diagram, one cause and one fix.

Author: Claude

Summary

  • Each container that Spark asks for must pass four limits: the size of one container, the AM pool, the share of the queue for one user, and the free memory on one node.
  • Each limit fails with a different symptom. The symptom tells you which setting to look at. You do not have to learn all the settings at once.
  • In yarn-cluster mode the Spark driver is the ApplicationMaster (AM). AMs use a separate, small pool: 10% of the queue by default.
  • An Oozie Spark action uses two AMs: the Oozie launcher and the Spark driver. The launcher keeps its AM for the full life of the Spark job. This can lock the AM pool.

Start here

Read the spark-submit output first. If spark-submit did not fail, run yarn application -status <appId> and read State and Diagnostics. Then select your case in the diagram.

executor memory ApplicationMaster (AM) used by other apps free request that waits or fails

Case 1: One container is too big

fails at once

What you see

spark-submit stops before the app starts. The error is Required executor memory (...) is above the max threshold (... MB) of this cluster! The same check applies to the driver AM.

Why

YARN does not give one container more than the cap. Spark asks for memory plus overhead, so --executor-memory must be smaller than the cap.

Fix

Make the executor or driver smaller, and use more executors. Or ask the admin to increase the cap.

yarn.scheduler.maximum-allocation-mb, yarn.scheduler.capacity.<queue-path>.maximum-allocation-mb

Case 2: The AM pool is full

ACCEPTED

What you see

State is ACCEPTED for a long time. Diagnostics: Queue's AM resource limit exceeded or User's AM resource limit exceeded. The queue does not look full.

Why

All AMs in a queue share a small pool: 10% of the queue by default. Normal containers cannot use this pool, and AMs cannot use the rest of the queue.

Fix

  • Find and kill old or stuck apps in the queue.
  • Use a smaller spark.driver.memory.
  • Ask the admin to increase yarn.scheduler.capacity.<queue-path>.maximum-am-resource-percent (for example to 0.3).

Case 3: Oozie launchers lock the AM pool

ACCEPTED, forever

What you see

The Oozie launcher app is RUNNING. Its Spark app is ACCEPTED with "AM resource limit exceeded". It often starts when several workflows start at the same time.

Why

One Oozie Spark action uses two AMs. The launcher (2 GB by default) keeps its AM until the Spark job ends. In yarn-cluster mode the Spark driver is the second AM.

Fix

  • Send the launchers to a different queue: <launcher><queue>oozie</queue></launcher> in the action.
  • Make the launcher smaller: oozie.launcher.memory.mb (older name: oozie.launcher.yarn.app.mapreduce.am.resource.mb). It only runs spark-submit.
  • Increase the AM percent of the queue (Case 2).

Case 4: You reached your user limit

RUNNING, few executors

What you see

The app is RUNNING with fewer executors than you asked for. Your usage stops at the queue capacity. Other parts of the cluster are idle.

Why

With user-limit-factor = 1, one user can never use more than the queue capacity, "irrespective of how idle the cluster is". On EMR most jobs run as the user hadoop, so all of them share this one limit.

Fix

First, make sure that you did not set the limit yourself: check spark.executor.instances and spark.dynamicAllocation.maxExecutors.

Then ask the admin to increase yarn.scheduler.capacity.<queue-path>.user-limit-factor (for example to 2), or use a queue with more capacity. Check that maximum-capacity is also larger than capacity.

Case 5: No single node has room

RUNNING, executors wait

What you see

The app is RUNNING. Some executors start, others wait. The queue and the user are below their limits.

Why

Each node gives YARN only yarn.nodemanager.resource.memory-mb. Large containers need one node with that much free memory. The free memory is in small parts on many nodes.

Fix

Use smaller executors (more of them), wait for other apps to end, or add nodes. Run yarn node -list -showDetails to see the free memory on each node.

How the five cases fit together

Each container request goes through four checks in this order. The Oozie case is Check 2 with two AMs for each job.

Commands to find the case

# 1. State and Diagnostics of one app (Cases 2, 3)
yarn application -status <appId>

# 2. All apps that wait or run, to see who uses the queue (Cases 2, 3, 4)
yarn application -list -appStates ACCEPTED,RUNNING

# 3. Capacity and usage of a queue (Case 4)
yarn queue -status <queue>

# 4. Free memory on each node (Case 5)
yarn node -list -showDetails

The ResourceManager web UI shows the same data. The Scheduler page shows each queue with its AM limit and user limit.

See all these settings on your EMR cluster

The script scripts/yarn_spark_settings.py reads yarn-site.xml, capacity-scheduler.xml, spark-defaults.conf and oozie-site.xml. It shows each setting with its value, its meaning and its case. On EMR it also shows the cluster ID and the instance groups, and it reads the AM pool, the queue usage and the free memory on each node from the ResourceManager. It uses only Python 3 and changes nothing.

Option 1: on the primary node. Connect with SSM or SSH, then run:

aws ssm start-session --target <primary-node-instance-id>   # or: ssh hadoop@<primary-node-dns>
curl -O https://raw.githubusercontent.com/ryandam9/Guides/master/scripts/yarn_spark_settings.py
python3 yarn_spark_settings.py | less

If the node has no internet access, copy the script through S3 with aws s3 cp.

Option 2: as an EMR step. The step runs on the primary node. Read the output in the console (Steps, then stdout) or in the step's log folder in S3.

aws s3 cp yarn_spark_settings.py s3://<bucket>/tools/
aws emr add-steps --cluster-id j-XXXXXXXX --steps \
  'Type=CUSTOM_JAR,Name=yarn-settings,ActionOnFailure=CONTINUE,Jar=command-runner.jar,Args=[bash,-c,"aws s3 cp s3://<bucket>/tools/yarn_spark_settings.py /tmp/ && python3 /tmp/yarn_spark_settings.py"]'
